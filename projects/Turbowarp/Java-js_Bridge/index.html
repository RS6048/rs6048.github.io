Java-js Bridge

Ongoing Updated: 2026-09-29

This project solves a long-standing pain point of TurboWarp projects: direct access to local files. By combining a custom extension with a JCEF (Java Chromium Embedded Framework) host, it bridges the sandboxed project to the host filesystem in a controlled, secure way.

The Problem

TurboWarp compiles Scratch projects into fast JavaScript/WebAssembly and runs them inside an ordinary browser sandbox. Web security rules deliberately prevent a page from silently reading arbitrary files on the host machine:

  • fetch("file://...") is blocked by browsers for security reasons.
  • The official File System Access API requires a user gesture and a file-picker dialog for every single file, which is unusable when a project wants to auto-load a whole folder of textures, sound banks or save data.

As a result, a TurboWarp project running locally still behaves like a website: no reliable access to the files next to it.

The Solution: JCEF + Custom Extension Bridge

Instead of fighting the sandbox, we replace the browser itself. JCEF is the Java port of the Chromium Embedded Framework: it embeds a full Chromium browser inside a Swing/JavaFX application and exposes native capabilities that an ordinary web page never has:

  • Custom scheme handlers — register a private protocol (e.g. tw-file://) and intercept its requests in Java code.
  • JavaScript extension registration — CefRegisterExtension() injects a native API object into every frame before the DOM exists.
  • Bidirectional message routing — CefMessageRouter / process messages carry asynchronous calls between the page (renderer) and the host (browser process).
  • Full JDK access — the Java side can use java.io and java.nio.file freely.

The bridge chain is: TurboWarp project → custom extension (JS) → JCEF bridge → Java host → local file.

How It Works

  1. The host application starts an embedded Chromium window through JCEF and loads the TurboWarp editor/project.
  2. A custom TurboWarp extension is loaded into the project; it exposes a small JS API such as twFile.read(path) (and may register a tw-file:// scheme as well).
  3. When the project calls the API, the renderer forwards the request through the CEF message router to the browser process.
  4. The Java side validates the path against an allow-listed root directory (blocking .. traversal and unexpected file types), then reads the file with java.nio.file.Files.
  5. The content is returned asynchronously — plain text, or base64 for binary — and resolved as a promise inside the project. Images, audio and save data are then available to the TurboWarp project as if they were local.

Security Notes

Reading files at will is a double-edged sword (a historical TurboWarp Desktop bug, CVE-2023-40168, allowed a malicious project to exfiltrate arbitrary files). The bridge therefore:

  • Only serves paths inside a configured root folder — no .. traversal, no absolute paths outside the root.
  • Validates file extensions against a whitelist.
  • Requires explicit user consent before the bridge is enabled.
